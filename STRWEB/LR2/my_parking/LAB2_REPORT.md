# Лабораторная работа №2. Тестирование SmartParking Solutions

## 1. Состав набора

В проекте подготовлено 111 независимых проверок. Новые проверки разделены по уровням:

| Файл | Уровень | Назначение |
|---|---|---|
| `test_unit_lab2.py` | Модульный | Изолированная проверка валидаторов, правил промокода, определения роли и логики погодных рекомендаций |
| `test_integration_lab2.py` | Интеграционный | Взаимодействие моделей с БД, каскадное удаление, уникальность начислений, HTTP-запросы Django, каталог услуг, отзывы и OpenWeather |
| `test_scenarios_lab2.py` | Сценарный | Жизненный цикл автомобиля и последовательность «начисление → платёж → баланс» |

Файлы `test_models.py`, `test_forms.py`, `test_views.py` и `test_admin.py` сохранены и исправлены так, чтобы ожидания соответствовали фактическим правилам приложения.

## 2. Arrange–Act–Assert

Новые проверки явно разделены на три части:

- **Arrange** — подготовка пользователя, сущностей, входных данных и заглушек;
- **Act** — выполнение одного действия или очередного шага сценария;
- **Assert** — проверка результата, состояния БД, HTTP-статуса или вызова зависимости.

Названия описывают условие и ожидаемое поведение, например:

- `test_duplicate_monthly_accrual_is_rejected`;
- `test_home_remains_available_when_weather_http_call_fails`;
- `test_full_car_lifecycle_through_http_endpoints`.

## 3. Параметризация и негативные случаи

Параметризация выполнена средствами `subTest` стандартного `unittest`. Одним методом проверяются наборы:

- допустимых и недопустимых телефонных кодов;
- корректных и некорректных госномеров;
- погодных условий и соответствующих рекомендаций;
- сочетаний категории и диапазона цены;
- отрицательных, нечисловых и обратных ценовых границ;
- комбинаций признаков аутентификации и суперпользователя.

Негативные и граничные проверки включают:

- неверный формат телефона и госномера;
- обратный интервал действия промокода;
- одинаковые даты начала и окончания промокода;
- повторное начисление за один период;
- нулевые, отрицательные и нечисловые значения;
- недоступность внешнего погодного сервиса;
- попытку клиента изменить чужой автомобиль;
- минимальные и максимальные допустимые значения моделей и форм.

## 4. Моки и HTTP-заглушки

В модульных проверках функции `home` зависимости заменены через `unittest.mock.patch`:

- `News.objects.first`;
- `Car.objects.count`;
- `requests.get`;
- `django.shortcuts.render`, импортированный в `parking.views`.

Это изолирует проверяемую логику от БД, шаблонизатора и сети.

В интеграционных проверках приложение вызывается через Django Client, а только внешний вызов `parking.views.requests.get` заменяется HTTP-заглушкой. Проверяется как успешный ответ OpenWeather, так и исключение `requests.Timeout`. Реальные сетевые обращения во время запуска набора отсутствуют.

## 5. Интеграция с БД

Интеграционные проверки используют временную БД Django и подтверждают:

- сохранение связанных автомобилей, начислений и платежей;
- вычисление финансового результата;
- запрет повторного начисления за один месяц и год;
- каскадное удаление финансовых записей;
- освобождение места после удаления автомобиля;
- фильтрацию услуг средствами ORM;
- сохранение отзыва после HTTP POST.

`django.test.TestCase` создаёт изолированное состояние для каждого метода и откатывает изменения, поэтому проверки не зависят друг от друга и от порядка запуска.

## 6. Сценарии переходов

### Жизненный цикл автомобиля

Сценарий соответствует диаграмме состояний лабораторной работы №1:

```text
Автомобиль отсутствует
→ создание без места
→ назначение первого места
→ перенос на второе место
→ освобождение места
→ повторное назначение
→ удаление автомобиля и освобождение места
```

Переходы создания, изменения и удаления выполняются через реальные HTTP-маршруты приложения. После каждого шага проверяются `Car.current_spot` и `ParkingSpot.is_occupied` в БД.

### Финансовый сценарий

```text
Сотрудник создаёт начисление 300
→ клиент регистрирует платёж 125
→ кабинет показывает баланс 125 − 300 = −175
```

Сценарий проверяет взаимодействие ролей, форм, представлений и связанных записей БД.

## 7. Запуск

Обычный запуск:

```bash
python manage.py test parking.tests -v 2
```

Измерение покрытия:

```bash
python -m coverage erase
python -m coverage run manage.py test parking.tests
python -m coverage report -m
```

HTML-отчёт при необходимости:

```bash
python -m coverage html
```

## 8. Настройка покрытия

Файл `.coveragerc` включает branch coverage и автоматически завершает команду ошибкой, если итог меньше 70%.

Из подсчёта исключены:

- `parking/migrations/*` — миграции;
- `parking/tests/*` — сами проверки;
- `parking/apps.py` — конфигурация Django-приложения;
- `parking/urls.py` — конфигурация маршрутизации;
- пакет `core` не входит в `source = parking`, поэтому настройки и WSGI/ASGI-конфигурация также не учитываются.
